# Page Purpose

The Features page helps a contractor confirm that TULBOXX can support the work their business needs to do.

The visitor has already learned why TULBOXX exists, how the platform stays connected, and what one complete workflow feels like. This page can now go deeper into individual capabilities.

Every feature must be explained through an outcome, demonstrated with real product UI, and connected back to the larger workflow.

This page is detailed.

It should never feel like a feature dump.

## Editorial Ownership

This page owns capability proof, organized around Win Work, Run the Work, Stay Organized, and Get Paid. It may reference the connected platform and contractor-control principles, but it should not retell the full philosophy or Morgan Lee workflow.

# Global Page Rules

- Lead every capability with the result it creates.
- Use current approved product UI as proof.
- Keep the contractor's work visible around the product.
- Show one meaningful action per product view.
- Explain how each feature connects to the rest of the platform.
- Never list a capability that has not been verified.
- Separate available, limited, beta, planned, and unsupported capabilities before launch.
- Do not use icon grids as the primary presentation.
- Do not repeat the full How It Works story.
- End by helping the visitor identify the solution that fits their trade or company.

# Feature Organization

Organize features around four business outcomes rather than software categories.

## Win Work

- Customer and opportunity capture
- Project information
- Estimating

## Run the Work

- Field access

## Stay Organized

- Customer history
- Daily priorities or next actions
- Connected communication
- Reporting

- Integrations

## Get Paid

- Payment requests and processing
- Outstanding balances

# Visual System for This Page

## Canonical References

- [`VISUAL_STORYBOARD.md`](VISUAL_STORYBOARD.md) governs visual storytelling and image-generation direction.
- [`docs/TULBOXX_BRAND_STYLE_GUIDE.pdf`](docs/TULBOXX_BRAND_STYLE_GUIDE.pdf) governs brand colors, typography, and logo treatment.

## Page Character

The Features page should feel:

- Detailed but not dense
- Product-led but grounded in real work
- Capable but approachable
- Scannable without becoming a card catalog
- Consistent without repeating the same layout

## Feature Presentation Pattern

Each primary feature should include:

1. Outcome headline
2. Short practical explanation
3. Real approved product UI
4. Real-world context image when it improves understanding
5. Connection to the larger workflow
6. Product verification status before launch

## Visual Rhythm

Avoid repeating image-left, copy-right for every section.

Use a controlled mix of:

- Large product spotlight
- Field-and-product composition
- Contractor/customer side-by-side
- Workflow transition
- Before/assist/review/after demonstration
- Quiet text-forward capability list
- Full-width outcome statement

## Product Screenshot Rules

- Crop intentionally.
- Keep relevant text readable.
- Use one action per screen.
- Use fictional demonstration data.
- Preserve customer and project continuity when helpful.
- Show real states, not idealized mockups.
- Never fabricate a capability.
- Record the product version used for every capture.

## Mobile Product Visuals

Mobile should appear frequently because TULBOXX is field-first.

Aim for an approximately balanced mix of mobile and desktop/tablet views across the page, adjusted to match where each workflow actually occurs.

## Photography Rules

- Use authentic contractors, trades, properties, equipment, and work conditions.
- Photography must explain where or why the feature matters.
- Generated imagery must follow the realism guidance in `VISUAL_STORYBOARD.md`.
- Never generate readable UI or paperwork inside a photograph.
- Never present generated people as customers or testimonials.

## Motion Rules

- Use motion for transformation, status change, connection, or progress.
- Keep videos short and focused on one idea.
- Avoid constant floating, parallax, rotation, or decorative 3D effects.
- Provide static fallbacks and respect reduced-motion preferences.

# Feature Verification Matrix

Before production, create a working matrix with one row per capability.

## Required Fields

| Field | Purpose |
|---|---|
| Public feature name | Customer-facing terminology |
| Outcome | Why the contractor cares |
| Current status | Available, limited, beta, planned, or unsupported |
| Supported platforms | Desktop, mobile web, native mobile, or other confirmed surface |
| User role | Who can view or act |
| Trigger | What starts the behavior |
| Contractor action | What the user must decide or confirm |
| Customer experience | What the customer sees |
| Connected records | Which customer, project, job, invoice, or payment context is preserved |
| Limitations | Important boundaries or exceptions |
| Proof source | Product owner, documentation, test account, or release reference |
| Approved screenshot | Exact capture supporting the claim |

## Publication Rule

Only capabilities marked available, limited with clear disclosure, or approved beta may appear as current launch features.

Planned and unsupported capabilities must not appear in present-tense marketing copy.
