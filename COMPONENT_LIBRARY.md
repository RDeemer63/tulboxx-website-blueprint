# COMPONENT_LIBRARY.md

# TULBOXX Marketing Component Library

**Version:** 1.0
**Status:** Canonical
**Purpose:** Define the reusable storytelling, conversion, proof, product, and navigation components used across the TULBOXX marketing website.

---

# Why This Exists

The TULBOXX website should feel like one connected system.

That means we should not design every page independently.

Pages should be assembled from a consistent family of components that share the same:

* Visual language
* Spacing
* Typography
* Interaction patterns
* Storytelling philosophy
* Conversion philosophy

Consistency builds familiarity.

Familiarity reduces friction.

But consistency does not mean repetition.

The same component may support different stories, layouts, images, and copy depending on the page.

---

# Component Rule

Every component must have a job.

A component should primarily do one of six things:

1. Create recognition.
2. Explain.
3. Demonstrate.
4. Prove.
5. Overcome an objection.
6. Move the visitor forward.

If a section does none of these things, reconsider whether it belongs.

---

# Component Hierarchy

Components fall into seven families:

```text
Navigation
    ↓
Hero
    ↓
Story
    ↓
Product
    ↓
Proof
    ↓
Decision
    ↓
Conversion
```

Pages should use only the components necessary to tell their story.

Do not build pages by checking boxes from this library.

# 2. Announcement Bar

## Purpose

Highlight something genuinely important.

Examples:

* New product release
* Beta availability
* Major feature
* Limited launch offer

## Rule

If there is nothing worth interrupting the visitor for, do not display one.

Never maintain an announcement bar simply because SaaS websites commonly have them.

---

# 3. Primary Hero

## Purpose

Answer three questions immediately:

1. What is this?
2. Is it for me?
3. Why should I care?

## Structure

Eyebrow — optional

Headline

Supporting copy

Primary CTA

Secondary CTA — optional

Trust cue

Primary visual

## Copy Rule

The headline sells the outcome.

The supporting copy explains how TULBOXX helps create it.

Do not put the feature list in the hero.

## Visual Rule

Use either:

* Contractor + product composition
* Strong product demonstration
* Purposeful workflow visualization

Never use abstract SaaS artwork.

---

# 4. Narrative Hero

## Purpose

Open story-driven pages such as:

* Why TULBOXX
* About
* Customer Stories

## Difference From Primary Hero

The primary hero explains the product.

The narrative hero creates emotion.

It may use a more editorial layout and stronger photography.

# 5. Recognition Section

## Purpose

Make the contractor feel understood.

## Typical Structure

Strong headline

2–4 short paragraphs

Real-world visual

## Example Territory

The goal is recognition.

Not exaggeration.

# 6. Problem Stack

## Purpose

Show several connected frustrations without turning them into a generic feature checklist.

## Possible Problems

* Estimates waiting until nighttime
* Customer information scattered across texts
* Photos buried in the camera roll
* Follow-ups forgotten
* Jobs living in someone's head
* Invoices sent late

## Visual

Problems may appear scattered before being visually consolidated.

## Rule

Do not create fear.

Create recognition.

# 10. Product UI Frame

## Purpose

Display TULBOXX consistently throughout the site.

## Desktop Treatment

Browser/app frame should be minimal.

Avoid fake browser chrome unless necessary for context.

## Mobile Treatment

Use realistic phone proportions.

## Rules

* Use real or approved product UI.
* Crop intentionally.
* Highlight only what matters.
* Avoid tiny unreadable full-screen screenshots.
* Never fabricate capabilities.

# Page Assembly Principles

Pages should not use every component.

A typical page may follow:

```text
Hero

↓

Recognition

↓

Transformation

↓

Product Demonstration

↓

Proof

↓

Objection Handling

↓

Conversion
```

But page strategy determines the final sequence.

Never force the story into a template.

---

# Section Rhythm

Avoid:

```text
Card Grid

Card Grid

Card Grid

Card Grid
```

The visual rhythm should change as the story develops.

Use combinations of:

* Full-width statements
* Editorial layouts
* Product demonstrations
* Photography
* Timelines
* Proof
* Interactive sections
* Quiet whitespace

Pages should feel paced.

---

# Copy Density

Not every section needs bullets.

Not every section needs three cards.

Not every section needs a headline plus subheadline plus paragraph.

Use the amount of copy the idea requires.

No more.

No less.

Longer narrative sections are appropriate when emotion or explanation matters.

---

# Mobile Rule

Every component must be designed for mobile intentionally.

Not merely stacked after desktop design is complete.

Remember the audience.

Many visitors will discover and evaluate TULBOXX from a phone.

Mobile is a first-class experience.

---

# Accessibility

Components should support:

* Keyboard navigation
* Visible focus states
* Sufficient contrast
* Reduced-motion preferences
* Semantic structure
* Screen readers
* Useful alt text

Accessibility is part of quality.

Not an afterthought.

---

# Performance

Do not sacrifice speed for visual novelty.

Heavy animation libraries, unnecessary video, oversized images, and excessive JavaScript should be challenged.

Performance communicates competence.

A business promising efficiency should have an efficient website.

---

# Component Naming

Implementation names should describe function rather than page ownership.

Prefer:

```text
OutcomeHero
WorkflowTimeline
ProductSpotlight
CustomerStory
TransformationSection
ROICalculator
FinalCTA
```

Avoid:

```text
HomepageSectionThree
BlueBox
CoolAnimation
FeatureThing
```

Components should remain understandable outside the page where they were created.

---

# Component Reuse

Reuse should create consistency.

It should not create sameness.

Allow controlled variants for:

* Alignment
* Media type
* Background treatment
* Density
* Product orientation
* Proof placement

Do not create a new component because the padding changed.

Do not force unrelated stories into the same component merely to maximize reuse.

---

# Codex Implementation Rule

Before creating a new marketing component, Codex should ask:

1. Does an existing component already solve this communication problem?
2. Can an existing component support this through an intentional variant?
3. Is the new component meaningfully different?
4. Does it follow the Design Principles?
5. Does it work intentionally on mobile?
6. Does it serve the page story?

If the answer supports a new component, create it.

Otherwise reuse the existing system.

---

# Component Quality Test

Before approving a component, ask:

**Purpose**
What job does it perform?

**Story**
Where does it move the visitor?

**Clarity**
Can someone understand it within seconds?

**Authenticity**
Does it feel built for contractors?

**Mobile**
Does it work naturally on a phone?

**Performance**
Is the complexity justified?

**Reuse**
Will this pattern be useful elsewhere?

If the component cannot answer those questions clearly, it is not finished.

---

# Final Principle

The component library exists to create consistency without creating sameness.

Visitors should never notice the component system.

They should simply experience a website that feels clear, intentional, connected, and unmistakably TULBOXX.

The system serves the story.

The story never serves the system.
