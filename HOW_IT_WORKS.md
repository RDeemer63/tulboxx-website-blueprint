# Page Purpose

This page walks the visitor through an actual contractor workflow.

It should show what using TULBOXX feels like from the first customer conversation through final payment. The visitor should see the same customer, project, information, and decisions moving forward without being recreated at every step.

This is not a feature tour.

It is one job, told clearly from beginning to end.

## Editorial Ownership

This page owns the practical first-call-to-final-payment demonstration through Morgan Lee's Backyard Drainage and Grading project. It should show the product in use rather than re-sell the philosophy, re-explain the information model, or become a feature inventory.

# Global Page Rules

- Tell one continuous job story.
- Begin with a customer and real work, not a dashboard.
- Use the same fictional project introduced on the Platform page.
- Show contractor actions wherever decisions or approvals are required.
- Show the customer's experience when communication or approval changes.
- Keep every product screen focused on one step.
- Never imply that every job must follow every step.
- Never imply automation that does not exist.
- Use AI only where it provides practical help and always show review.
- End with the visitor wanting deeper detail about individual capabilities.

# Demonstration Story

Use the same fictional story established in `PLATFORM.md`.

## Customer

Morgan Lee

## Project

Backyard Drainage and Grading

## Business Type

Landscaping or excavation contractor

## Starting Situation

Morgan calls after water begins collecting near the back of the house. The contractor schedules a site visit, takes photos and measurements, records a rough voice note, and needs to prepare a professional estimate.

## Work

The proposed work includes grading, drainage improvements, materials, equipment, labor, and restoration of the disturbed area.

## Outcome

Morgan reviews and approves the estimate. The contractor schedules and completes the work, documents the result, sends the invoice, and records payment.

## Demonstration Data Rule

Every name, address, date, message, photo, measurement, line item, price, approval, invoice, and payment state must be fictional, realistic, internally consistent, and approved before production.

This scenario is illustrative. It must not imply that every product capability is currently available until each state has been confirmed.

# Section 9 - The Work Decides the Path

## Stage

Readiness

## Question Answered

Do I have to use every step for every job?

## Copy

**Eyebrow**

Not every job works the same way.

**Headline**

Use the steps the work needs. Skip the ones it does not.

**Body copy**

The drainage project followed a full estimate-to-payment path.

Another customer may need a quick repair, time-and-material work, a verbal price, or a job that begins without a formal estimate.

TULBOXX follows the path the job needs instead of forcing every customer through the same pipeline.

## Example Paths

### Full Project

```text
Customer → Site Visit → Estimate → Approval → Schedule → Job → Invoice → Payment
```

### Quick Service Job

```text
Customer → Work → Invoice or Payment
```

### Time-and-Material Work

```text
Customer → Scheduled Work → Recorded Work → Invoice → Payment
```

## Editorial Boundary

Keep these alternate paths because they prevent the Morgan Lee demonstration from looking mandatory. Do not restate the broader progressive-structure philosophy owned by Why TULBOXX.

## Visual Direction

**Asset ID:** `WORKFLOW-FLEX-09`

**Purpose**

Prevent the main demonstration from being mistaken for a required rigid pipeline.

**Format**

A simple branching path using confirmed product-supported routes.

**Direction**

Begin with one shared customer and show three possible paths based on the job. Keep the full-project path visible as one option, not the default every user must follow.

**Verification rule**

Every alternate path must be tested against current product behavior before launch.

## Exit Condition

The visitor should think:

> The system can follow the job instead of making the job follow the system.

# Visual System for This Page

## Canonical Reference

Use [`docs/TULBOXX_BRAND_STYLE_GUIDE.pdf`](docs/TULBOXX_BRAND_STYLE_GUIDE.pdf) for brand colors, typography, logo treatment, and overall visual character.

Use [`PHOTOGRAPHY_DIRECTION.md`](PHOTOGRAPHY_DIRECTION.md) for all photographic art direction, generation, selection, cropping, and post-processing.

## Page Character

The page should feel:

- Familiar
- Sequential
- Practical
- Product-led
- Easy to follow
- Grounded in real fieldwork

## Story Continuity

Continuity is the primary design system for this page.

Preserve:

- The same customer name
- The same project title
- The same fictional property
- The same project photography
- Logically consistent dates
- Logically consistent scope and pricing
- The same estimate, job, invoice, and payment relationship

The page fails if it looks like eleven unrelated product demonstrations.

## Photography Direction

- Use one property and one realistic drainage project whenever possible.
- Show credible site conditions, equipment, materials, and safe work practices.
- Use the same contractor or crew across the sequence when practical.
- Capture before, during, and after states.
- Never represent generated people as real customers.
- Composite real product UI into devices after image approval.

## Product UI Direction

- Use approved current product screens.
- Focus each screen on one action.
- Make visible UI text readable.
- Preserve project identity across all states.
- Show user review and confirmation.
- Never expose real customer data.
- Never redesign unsupported workflow states for marketing convenience.

## Motion Direction

- Motion should show one action causing the next state.
- Avoid autoplaying the entire workflow.
- Allow visitors to control or scroll through each step.
- Keep a clear static state for reduced motion.
- Do not use motion to hide unsupported transitions.

# Mobile Experience

- Show the active step and project name in a compact sticky label.
- Display one product action at a time.
- Pair each product state closely with the copy that explains it.
- Avoid side-by-side states that become unreadable; use a controlled before-and-after sequence.
- Keep the full workflow accessible without forced animation.
- Ensure customer and contractor views are clearly labeled.
- Make Explore Features available after completion without interrupting earlier steps.
- Preserve comfortable reading length and large actions for between-job use.

# Accessibility Requirements

- Use one semantic `h1` for the hero headline.
- Preserve logical heading order for steps.
- Provide a text version of the complete workflow.
- Do not rely on color to communicate active or completed steps.
- Label contractor and customer product views.
- Make progress navigation keyboard accessible.
- Announce step changes appropriately.
- Provide static alternatives to scroll-driven product transitions.
- Use meaningful alt text for jobsite and product images.
- Meet WCAG AA contrast at minimum.
- Respect reduced-motion and text-resizing preferences.

- Load step media as the visitor approaches each section.
- Use optimized focused captures rather than full-screen video.
- Reserve image and product-media dimensions.

# Page Acceptance Criteria

The page is ready for production when:

- One recognizable project runs through the entire page.
- The visitor can explain the workflow after viewing it once.
- Every step begins with familiar contractor behavior.
- Information visibly carries forward.
- Contractor decisions and review remain visible.
- Customer-facing states match contractor actions.
- The page does not imply every job requires every step.
- All shown product behavior is confirmed.
- The workflow remains understandable without motion.
- Product UI is readable on mobile.
- Jobsite imagery is accurate and safe.
- Explore Features feels like the natural next action.

---

# Final Test

The page should not leave the visitor thinking:

> That is a lot of software to manage.

It should leave them thinking:

> That follows the way my jobs already happen—and it would keep me from starting over at every step.

If the page does not create that belief, it is not finished.
